# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AI parental-control platform (ESPRIT PFE / internship project). Two independent apps in one repo:

- **`backend/`** — Node.js + Express + PostgreSQL API (TypeScript, ESM). Stores usage/screen metadata, computes daily scores, generates gamified missions.
- **`MobileApp/`** — React Native 0.74 Android app (TypeScript) with custom Java/Kotlin native modules. Does all sensitive processing (OCR, NSFW, keyword filtering) **on-device**; only extracted text + risk metadata leave the phone.

The privacy model is central: **no screenshot ever reaches the backend.** The device captures a screen, runs ML Kit OCR + `nsfwjs`/TFLite + a multilingual keyword filter, deletes the image, and POSTs only text metadata to `POST /api/screen-events`: a ≤500-char text preview, bounded numeric risk scores, an enum category, the app package/label, and a schema-bounded `imageClassificationDetails` object — a fixed set of named fields (classifier scores + model-label vocabulary), every string length-capped, unknown keys stripped and logged. The schema bounds the shape and size of what the device can send there (~2 KB of model output), not the semantics of each field; every field is server-validated in `backend/src/validators/screenEvents.validator.ts` (the ≤500-char cap enforced there **and** by the `VARCHAR(500)` column). **Mobile→backend coupling (handoff #15):** `source` and `captureQualityHint` are `.valid()` enums with no truncate escape — adding a `ClassificationSource` or a third `captureQualityHint` value on the device 400s **every** capture until the validator gains the value in the same commit; string fields elsewhere in the object `.truncate()` instead, and `mockHint` is accepted-but-stripped. Preserve this invariant when touching the capture pipeline.

## Commands

The two apps have separate toolchains — always `cd` into the right one. The shell is PowerShell on Windows.

### backend/
```powershell
npm run dev            # tsx watch src/index.ts (hot reload)
npm run build          # tsc -> dist/
npm start              # node dist/index.js
npm run db:up          # docker compose up -d (Postgres on host :5433 → container 5432)
npm run db:migrate     # tsx src/db/migrate.ts (ledger-tracked; safe to re-run any number of times)
npm run db:setup       # db:up + db:migrate
npm test               # jest (ts-jest, tests live in backend/tests/**.test.ts)
npm run test:watch
npx jest tests/scoringEngine.test.ts   # run one test file
```
`docker-compose.yml` maps host port **5433**→5432 specifically to avoid the local PostgreSQL 18 service on 5432; `.env.example` already points `DATABASE_URL` at 5433, so `npm run db:setup` works without stopping that service. `db/migrate.ts` keeps a **`schema_migrations` ledger** (created by the runner itself): each file runs once, inside its own transaction together with its ledger insert (fail → rollback → no row, no partial schema), and re-running is a safe no-op. Decision logic is the pure, DB-free `src/db/migrationPlan.ts` (tested by `tests/migrationPlan.test.ts`). Editing an already-applied file is detected by **checksum** and **refused** (exit 1), not silently re-run. A pre-ledger DB already at head (e.g. Helmi's demo DB) is auto-detected via landmark probes and **baselined** — every file stamped as applied, nothing executed. A *partially* migrated pre-ledger DB aborts with an actionable message; the operator picks up with `MIGRATE_BASELINE_UPTO=<file> npm run db:migrate` (stamp ≤ that file, run the rest). `docker compose down -v` is **no longer** a routine recovery path — only for deliberately discarding a database. See `backend/DATABASE.md` for more.

## Backend architecture

Entry: `src/index.ts` → `createApp()` (`src/app.ts`) → `src/routes/index.ts`.

- **Auth boundary**: `routes/index.ts` mounts `/health` and (non-prod) `/dev`, `/debug` publicly, then applies `verifyToken` middleware — **every route below that line requires `Authorization: Bearer <JWT>`**. JWT payload = `{ sub, role: 'parent'|'child', childId? }`.
- **Ownership authorization (ALL_IS_FIXED #7)** — `verifyToken` proves identity, not that the caller owns the `childId` they name. The **single** predicate is `userCanAccessChild(user, childId)` in `src/middleware/childAccess.ts` (child branch: `user.childId === childId`; parent branch: `parentOwnsChild(user.sub, childId)` = `SELECT 1 FROM children WHERE id=$1 AND parent_id=$2`, a PK probe — **not cached**, no invalidation story to own). Every earlier copy is gone (the `assertChildAccess` rubber-stamp whose *parent* branch was `return true` — 3 copies / 7 call sites — and the private `assertParentOwnsChild` in `child.routes.ts`). Child id arrives in **4 shapes**: `param` / `query` / `body` → the `requireChildAccess('<loc>:childId')` middleware factory (its returned fn is a **named** expression `requireChildAccessMw` so the enumeration test can see it); `derived` (from a loaded `missions` row) → an in-handler `userCanAccessChild` call in `approve`/`reject` after the row is fetched. **`tests/routeAuthorization.test.ts`** walks the mounted router and checks the **complete** table against a committed `ROUTE_INVENTORY` (symmetric — any route added/renamed/removed reds the suite until a human classifies it; that churn is the point) + per-class assertions + a `:childId`-path-can't-be-non-child belt-and-suspenders rule; **residual:** it cannot introspect a handler body, so the two `derived` routes are held by a source-text assertion (`userCanAccessChild(` present) + acceptance, not by chain inspection. **Failure = `403 {"error":"Access denied for this child"}`** uniformly (matches the pre-existing contract; adversary is another registered parent so a child UUID's existence is not a secret — 404 would churn the dashboard and collide with the genuine `404 "Mission not found"`). **`POST /missions/generate`**: a named `devOnlyRoute` runs **first** (flat `404` in production for everyone, *before* any role/body/ownership branch) — putting the ownership guard ahead of the old in-handler `isProduction` 404 would have made prod answer `403` vs `404` by ownership on an invisible route (the #8-SF4 failure class); then `requireParentRole` + `requireChildAccess('body:childId')`. **Behaviour delta:** the ~9 newly-guarded `param`/`query` routes now do a DB lookup — if it *throws*, the response is `500 {"error":"Authorization check failed"}` where a rubber stamp would have returned `200`; `child.routes.ts`'s 500-on-lookup-error body changed from `"Failed to fetch/update child …"` to the same. Happy paths and 403 paths unchanged. **This is authorization given a valid token — there is no authentication / registration / token-issuance route; the only JWT source is the unauthenticated `/api/dev/*-token`. Do not describe the API as "secured".**
- **Routes** (`src/routes/*.routes.ts`): `screen-events`, `usage`, `scores`, `missions`, `rewards`, `badges`, `bonus`, `custom-missions`, `child`.
- **Scoring** (`src/scoring/`): pure functions. `scoringEngine.ts` computes an **addiction risk score** (higher = worse; weighted intensity/compulsivity/night-usage/escalation/real-imbalance) and a **well-being score** (higher = better). `aggregateUsage.ts` turns raw `usage_sessions` rows into the daily stats those functions consume; `wellbeingProxies.ts` fetches DB-backed inputs (physical activity, bedtime variance, family interaction). Keep scoring functions pure and covered by `tests/scoringEngine.test.ts` / `wellbeingProxies.test.ts`.
- **Cron** (`src/jobs/dailyScoreJob.ts`): scheduled on server start (`node-cron`). Per child per day, aggregates sessions → computes both scores → writes `daily_scores` → may generate a mission from high addiction / low well-being.
- **Missions** (`src/services/`): `missionGenerator` (rule-based generation), `missionCompletion`, `gamificationService` (points/badges), `quizService`, `customMissionService`. Mission "risk cooldown" is now "a pending risky mission exists" — see `hasRecentRiskyMission`, not the legacy env var.
- **`POST /api/missions/dev/force` (ALL_IS_FIXED #6)** — dev-only route to force a specific mission template for a demo. Chain: `devOnlyRoute` **first** (flat `404` in production, before any role/body/ownership branch — same `#8-SF4` reason as `/generate`) → `requireParentRole` → `validateBody(forceMissionDevSchema)` → `requireChildAccess('body:childId')`. Inventoried in `ROUTE_INVENTORY` as `child:body`. Body: `{ childId, templateKey (a `.valid()` enum over `Object.keys(MISSION_TEMPLATES)` — unknown → 400), triggerReason? (default `risky_content`), category?, score? (default 75) }`. It calls `generateMissionForChild` directly with a new optional `MissionGenerationContext.forceTemplateKey` (`undefined` on every production path) which **bypasses the cooldown, the adaptive risk threshold, the pending limit, the random `pickMissionTemplate` draw and the age-based rewrite** (`forceTemplate` → `cloneTemplate`, skipping `buildTemplateFromPick`); quiz enrichment, escalation, the metadata object and the INSERT are unchanged. `expires_at` still comes from the column default (`007_missions_gamification.sql:13`, `NOW()+24h`), so the forced row is visible to `hasRecentRiskyMission` / `getActivePendingMission` and re-surfaces via `POST /api/screen-events`. **Verified backend-only:** a forced pending Tic-Tac-Toe mission is returned to a risky capture as a re-surfaced `newMission` (id + `metadata.game` + `reSurfaced:true`); device presentation (mobile `missionPresentationGuard`) remains unexercised — "#16 is reachable", not "unblocked end to end".
- **DB**: plain SQL migrations in `src/db/migrations/NNN_*.sql`, applied in filename order by `db/migrate.ts` and tracked in the `schema_migrations` ledger. `db/pool.ts` exports the `pg` pool + `query`. No ORM. Add schema changes as a **new numbered file** (zero-padded 3 digits) — never edit an applied one; the ledger now **enforces** this by checksum (a changed applied file aborts the run). Each file runs inside a transaction, so `CREATE INDEX CONCURRENTLY` / `ALTER TYPE … ADD VALUE` won't work in a migration.

## Mobile architecture

Entry: `App.tsx` → dev JWT bootstrap (`useDevChildToken`) → `NavigationContainer` → `AppNavigator` (`src/navigation/`). `RealUsageTracker` runs alongside the UI to report usage.

- **Native modules** (`src/native/*.ts` bridge to `android/.../com/mobileapp/`): `ScreenCapture` (MediaProjection foreground service), `ForegroundApp` (UsageStats — which app is in front), `NsfwTflite` (on-device NSFW), `OverlayMission` (draws a mission overlay over other apps), `overlayPermission`, `SafeGuardAccessibility` (AccessibilityService window/IME/scroll events — see below).
- **On-device analysis pipeline** (`src/services/`): OCR via `mixedScriptOcr.ts` / `mobileArabicOcr.ts` (ML Kit + UI-noise filter + Arabizi/Derja normalization), `nsfwClassifier.ts` + `imageClassifier.ts` (image risk), `keywordFilter.ts` (EN/FR/AR/Tunisian-Derja multilingual). Results combine into a `combinedRiskScore` that drives capture cadence and mission triggering.
- **Adaptive capture** (documented in `README.md`): capture frequency is risk-based, not fixed — app-switch triggers + a follow-up + a periodic fallback. App-switch triggers are **accessibility-window-driven** when the SafeGuard accessibility service is connected (near-instant), falling back to the 1s UsageStats poll otherwise (see the accessibility bullet below). **Periodic fallback (A3c-2): one native-driven clock.** The native capture loop no longer captures on its own timer — it emits `onNativePeriodicTick` (bare `{timestamp}`) every `NATIVE_TICK_INTERVAL_MS` (**5s as of A3c-3**, decoupled from `RISK_INTERVAL_HIGH_MS`) from the same `Handler.postDelayed` loop on `ScreenCaptureThread`, Doze-resistant because the `mediaProjection`-type foreground service keeps the process unfrozen for the whole session (no `AlarmManager`/`WorkManager`). **A3c-3 tick-rate fix:** A3c-2 set the tick to 10s (`= RISK_INTERVAL_HIGH_MS`) and claimed subsampling would realize every effective interval — false, `15000 % 10000 ≠ 0`, so a 15s browser_social target quantized up to the 20s tick (device-confirmed 33% slower browser scanning, a regression). 5s divides 10/15/20/120 exactly; native floor is a strict `intervalMs < 5_000` so 5000 passes with **no native change**. Expect a minor uptick in one-tick `DEBOUNCED`/`interval_floor` logs (5s tick landing on the 5s coordinator/native floor — self-correcting, non-cumulative, A3c-1-observable). **Device-confirmed 2026-09-02 ("Smoke B", first measured this session):** ~3 min of continuous a11y-driven Instagram scrolling produced 9 consecutive `periodic_fallback` captures at **exactly 15s** (`browser_social` clamp), zero quantization to 20s — the regression this fix targeted does not reproduce. `useScreenshotCapture` subsamples each tick via `shouldEmitPeriodicCapture(now, lastPeriodicPassAtRef, dynamicIntervalMsRef)` — pass only if `≥ dynamicIntervalMsRef` elapsed since the last pass and the target `> 0` — then routes survivors through `tryCaptureNow('PERIODIC_FALLBACK')`, the same coordinator door as every other reason (so periodic capture now gets keyboard-suppression, mission-pause, the 5s debounce and A3c-1 rejection handling, which the old direct-capture loop bypassed). `dynamicIntervalMsRef` is the effective adaptive interval from `computeEffectiveAdaptiveInterval` (`adaptiveCapture.ts`, unchanged): risk mean `>70→10s / >30→15s / else 20s`, then per-category clamp via `appCapturePolicy.ts` (`browser_social→≤15s`, `game`/`system→0` = periodic disabled, `education→≥120s`). The old JS `setTimeout` adaptive loop (`resetPeriodicTimer`/`scheduleTick`, `CaptureReason.PERIODIC_ADAPTIVE`) is **retired**; `PERIODIC_ADAPTIVE` removed from the enum. Invariant: **higher risk must scan at least as often as lower risk** (HIGH ≤ MEDIUM ≤ LOW interval). **Liveness backstop (A3c-2c):** the tick handler runs `decideTickAction(...)` (pure, `adaptiveCapture.ts`) *before* the subsample gate — if the JS OCR lock (`isProcessingRef`) has been held past `OCR_LOCK_LIVENESS_MS` (60s, **12 ticks** post-A3c-3, comfortably above the ~40s worst-case legit `processCapturedFrame` = 2.5s foreground + 25s vision + 12s POST) it calls the extracted `forceReleaseProcessingLock('tick-liveness')` and returns; otherwise it subsamples as before. **A3c-3 scroll-settle** rides the same `noop` ticks: on a tick that neither force-releases nor emits periodic, the handler runs pure `decideScrollSettle(...)` and may `tryCaptureNow('SCROLL_SETTLED')` (see accessibility bullet). This is the **only** stale-lock recovery that survives backgrounding — the in-frame `setTimeout`/`setInterval` watchdogs are RN-frozen there. **Scope correction (D3 device smoke, 2026-09-03):** "survives backgrounding" means *app-backgrounded, screen-on* only — device-measured firing at `elapsed≈60000` there, but at `elapsed:195233` (i.e. only on screen-on thaw) when the screen was slept. MIUI freezes the RN JS thread on screen-off despite the FGS, so a frame that wedges while the phone is locked is unrecovered until the screen wakes. See D1 follow-up debt item 5. See frame-skip-gate Debt (4).
- **Capture coordinator** (`src/capture/captureCoordinator.ts`): every capture trigger in `useScreenshotCapture.ts` (`tryCaptureNow`, `triggerAppSwitchCapture`, follow-up, periodic tick, deferred re-issue) **must call `coordinatorRef.current.requestCapture(reason: CaptureReason)` before invoking native `captureNow`**, and route coalesced retries via `takePendingReason()`. The coordinator is a pure factory (`createCaptureCoordinator(deps)`, no React/native imports, injected clock) owning: request debounce (`CAPTURE_DEBOUNCE_MS` 5s, `FOLLOW_UP_MIN_GAP_MS` 2s for `APP_SWITCH_FOLLOW_UP` — both now live only here), mission-pause gating **for requests**, keyboard-suppression gating **for requests** (`setKeyboardVisible(bool)`; while true, `requestCapture` drops **only** the three `isKeyboardSuppressibleReason` reasons — `PERIODIC_FALLBACK`, `CONTENT_CHANGE`, `SCROLL_SETTLED` — returning `CaptureSkipReason.KEYBOARD_SUPPRESSED`; every app-switch reason, `BROWSER_NAVIGATION`, `RISK_FOLLOW_UP` and `APP_SWITCH_FOLLOW_UP` still pass so safety monitoring never stops while typing), and priority-based coalescing of one pending reason while OCR is busy (`requestCapture` decision order: `NOT_MONITORING` → `MISSION_PAUSED` → `KEYBOARD_SUPPRESSED` → `BUSY_DEFERRED`/`SUPERSEDED` → `DEBOUNCED` → allowed). `isKeyboardSuppressibleReason` is the **only** place that three-reason list is written (unit-tested over all 11 members); `reset()` also clears `keyboardVisible`. `CaptureReason` has 11 members (A3c-2 removed `PERIODIC_ADAPTIVE`; `PERIODIC_FALLBACK` wired to the native tick; `SCROLL_SETTLED` wired in A3c-3, tier-2, keyboard-suppressible, non-force); 4 (`MISSION_RESUME`, `RISK_FOLLOW_UP`, `CONTENT_CHANGE`, `BROWSER_NAVIGATION`) are declared for later wiring, and `CAPTURE_REASON_PRIORITY` leaves value 4 unused where `PERIODIC_ADAPTIVE` was. **Native-rejection handling** (A3c-1): the hook subscribes to the `onScreenCaptureRejected` bridge event (`{reason, elapsedMs?, timestamp}`, `reason` = `NativeRejectionReason` `'interval_floor' | 'busy'`) and calls `coordinator.onNativeRejected(reason)`. That method **never advances `lastAcceptedAtMs`** (no frame was accepted) and never touches `pendingReason`; for `'interval_floor'` it clears the coordinator's **force-arm mirror** (`forceArmedReason`, exposed via `isForceArmed()`), which is set whenever `requestCapture` allows an `isForceCaptureReason` reason and also cleared by `onFrameAccepted` and `reset()`. `'busy'` is log-only (an in-flight native frame consumes the real flag). Bridge events are not timer-dependent, so this still lands after RN unfreezes JS timers on foreground. **Inbound-frame guards stay in `processCapturedFrame`** — the OCR lock (`isProcessingRef`), generation token / `isActive()`, `OCR_LOCK_TAKEOVER_MS`, both watchdogs, the A3c-2c tick-liveness backstop (which force-releases the lock from the native tick when backgrounded — see the adaptive-capture bullet), and the inbound `isMissionCapturePaused()` check are NOT the coordinator's job (frames can still overlap/arrive stale even though every `captureNow` is now JS-initiated post-A3c-2). **Owed-force debt (A3d — never drop a tier-0 intent):** device evidence showed a genuine app switch (e.g. launcher → search → Instagram, both switches inside 5s) has its *second* switch silently `DEBOUNCED` — `requestCapture` returned before `tryCaptureNow` ever reached `forceNextCapture()`, so the new app's hash-gate baseline was never established and every capture for the rest of that session (55s observed) hit `frame.skipped.unchanged` against the *previous* app's frame. Fix: `requestCapture` now tracks a private `forceCaptureOwed` boolean (no TTL — `HASH_STALENESS_MS` 90s is already a backstop) — a `DEBOUNCED` decision for an `isForceCaptureReason` reason sets it; the *next* allowed decision of **any** reason consumes it and returns `force: true` (new field on the `CaptureDecision` allowed variant, replacing the hook's old direct `isForceCaptureReason(decision.reason)` check — `tryCaptureNow` now reads `decision.force`). `onNativeRejected('interval_floor')` **re-owes** the debt whenever `forceArmedReason` was set at rejection time (covers both a paid-down debt and a direct tier-0 reason that native's own floor rejected) — this deliberately reverses the pre-A3d assumption that a floor-rejected tier-0 attempt is simply gone; see the rewritten test in `captureCoordinator.test.ts`. `resumeCapture` does **not** clear the debt (a switch missed before a mission pause is still missed after it); `reset()` does. No new `CaptureReason`, no native change — `forceNextCapture()` already was a one-shot hash-gate bypass; the fix is *when* it gets armed. A parallel "blank/stale capture" hypothesis (raised by the same device evidence: hamming=1 five times against a non-blank reference frame is suspicious on its own) was **ANSWERED, closed 2026-09-02, negative.** The MediaProjection stale-token native pass added the raw dHash value to the `frame.skipped.unchanged` log; the next rapid-switch-then-scroll repro (this time with the accessibility service genuinely bound, confirmed via `a11y.window.accepted`) reran the exact scenario — ~3 min of active Instagram scrolling, 9 consecutive periodic captures, **zero `frame.skipped.unchanged` in the window, every capture a fresh distinct frame.** The dead/stale-capture-source hypothesis does not hold; do not re-open absent new device evidence. Pure logic covered by `__tests__/captureCoordinator.test.ts`.
- **Mission capture session lease (ALL_IS_FIXED #2)** (`src/utils/missionCaptureSession.ts` + `useScreenshotCapture.ts` + `useMissionOverlayListener.ts` + `presentMissionFromCapture.ts` + `MissionScreen.tsx`): while a mission blocks the screen (overlay or `MissionScreen`), capture must stay paused — `isMissionCapturePaused()` gates `captureCoordinator`'s `MISSION_PAUSED` check above, plus several early-returns in `useScreenshotCapture.ts`. Was a bare `sessionDepth` counter with no identity and only one balanced-decrement call site (`endMissionCaptureSession`, confirmed dead — zero callers besides its own definition — removed); every real release went through unconditional `forceEndMissionCaptureSession()`. **Now a single nullable lease** `{missionId, source: 'overlay'|'screen'|'fallback', startedAtMs}`, still a pure module-level singleton — bare exports delegate to one `createMissionCaptureSessionTracker(deps)` instance, the same factory-with-injected-clock shape as `a11yHealth.ts`, so the test file injects a fake clock without touching any caller. `begin(missionId, source)` is idempotent for the same id+source (no-op); a source change (the overlay→`MissionScreen` handoff) **re-stamps** `startedAtMs` to now rather than preserving the original time — a source change is evidence of a live owner, and preserving the original stamp risked the backstop firing mid-mission. `forceEnd()` stays unconditional and id-agnostic **by design** — every real release site means "this mission flow is over, whatever it was"; an id-scoped release would fail toward a wedge, unconditional release fails toward more monitoring, the correct direction. `missionId` exists for idempotence and diagnostics, not scoped release.

## Working across both apps
