# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AI parental-control platform (ESPRIT PFE / internship project). Two independent apps in one repo:

- **`backend/`** — Node.js + Express + PostgreSQL API (TypeScript, ESM). Stores usage/screen metadata, computes daily scores, generates gamified missions.
- **`MobileApp/`** — React Native 0.74 Android app (TypeScript) with custom Java/Kotlin native modules. Does all sensitive processing (OCR, NSFW, keyword filtering) **on-device**; only extracted text + risk metadata leave the phone.

The privacy model is central: **no screenshot ever reaches the backend.** The device captures a screen, runs ML Kit OCR + `nsfwjs`/TFLite + a multilingual keyword filter, deletes the image, and POSTs only text (≤500 chars) + risk flags to `POST /api/screen-events`. Preserve this invariant when touching the capture pipeline.

## Commands

The two apps have separate toolchains — always `cd` into the right one. The shell is PowerShell on Windows.

### backend/
```powershell
npm run dev            # tsx watch src/index.ts (hot reload)
npm run build          # tsc -> dist/
npm start              # node dist/index.js
npm run db:up          # docker compose up -d (Postgres on host :5433 → container 5432)
npm run db:migrate     # tsx src/db/migrate.ts (ledger-tracked; safe to re-run any number of times)
npm run db:setup       # db:up + db:migrate
npm test               # jest (ts-jest, tests live in backend/tests/**.test.ts)
npm run test:watch
npx jest tests/scoringEngine.test.ts   # run one test file
```
`docker-compose.yml` maps host port **5433**→5432 specifically to avoid the local PostgreSQL 18 service on 5432; `.env.example` already points `DATABASE_URL` at 5433, so `npm run db:setup` works without stopping that service. `db/migrate.ts` keeps a **`schema_migrations` ledger** (created by the runner itself): each file runs once, inside its own transaction together with its ledger insert (fail → rollback → no row, no partial schema), and re-running is a safe no-op. Decision logic is the pure, DB-free `src/db/migrationPlan.ts` (tested by `tests/migrationPlan.test.ts`). Editing an already-applied file is detected by **checksum** and **refused** (exit 1), not silently re-run. A pre-ledger DB already at head (e.g. Helmi's demo DB) is auto-detected via landmark probes and **baselined** — every file stamped as applied, nothing executed. A *partially* migrated pre-ledger DB aborts with an actionable message; the operator picks up with `MIGRATE_BASELINE_UPTO=<file> npm run db:migrate` (stamp ≤ that file, run the rest). `docker compose down -v` is **no longer** a routine recovery path — only for deliberately discarding a database. See `backend/DATABASE.md` for more.

## Configuration you'll hit immediately

- **Backend env** (`backend/src/config/env.ts`): `DATABASE_URL` and `JWT_SECRET` are **required** (app throws on boot if missing). Others optional: `PORT` (3000), `NODE_ENV`, `JWT_ISSUER`.
- **Mobile → backend URL** (`MobileApp/src/config/apiConfig.ts`): `DEV_LAN_HOST` is currently `127.0.0.1` for a **USB device via `adb reverse`** (see build note above). For a phone on the same Wi-Fi instead, set it to your PC's Wi-Fi IPv4. Android emulator auto-uses `10.0.2.2`. `__DEV__` builds hit `http://<host>:3000`.
- **Auth in dev**: the app mints a child JWT via `/api/dev/*` routes (see `useDevChildToken`). Those `/dev` and `/debug` routes are registered **only when `NODE_ENV !== production`** (`routes/index.ts`).

## Backend architecture

Entry: `src/index.ts` → `createApp()` (`src/app.ts`) → `src/routes/index.ts`.

- **Auth boundary**: `routes/index.ts` mounts `/health` and (non-prod) `/dev`, `/debug` publicly, then applies `verifyToken` middleware — **every route below that line requires `Authorization: Bearer <JWT>`**. JWT payload = `{ sub, role: 'parent'|'child', childId? }`.
- **Routes** (`src/routes/*.routes.ts`): `screen-events`, `usage`, `scores`, `missions`, `rewards`, `badges`, `bonus`, `custom-missions`, `child`.
- **Scoring** (`src/scoring/`): pure functions. `scoringEngine.ts` computes an **addiction risk score** (higher = worse; weighted intensity/compulsivity/night-usage/escalation/real-imbalance) and a **well-being score** (higher = better). `aggregateUsage.ts` turns raw `usage_sessions` rows into the daily stats those functions consume; `wellbeingProxies.ts` fetches DB-backed inputs (physical activity, bedtime variance, family interaction). Keep scoring functions pure and covered by `tests/scoringEngine.test.ts` / `wellbeingProxies.test.ts`.
- **Cron** (`src/jobs/dailyScoreJob.ts`): scheduled on server start (`node-cron`). Per child per day, aggregates sessions → computes both scores → writes `daily_scores` → may generate a mission from high addiction / low well-being.
- **Missions** (`src/services/`): `missionGenerator` (rule-based generation), `missionCompletion`, `gamificationService` (points/badges), `quizService`, `customMissionService`. Mission "risk cooldown" is now "a pending risky mission exists" — see `hasRecentRiskyMission`, not the legacy env var.
- **DB**: plain SQL migrations in `src/db/migrations/NNN_*.sql`, applied in filename order by `db/migrate.ts` and tracked in the `schema_migrations` ledger. `db/pool.ts` exports the `pg` pool + `query`. No ORM. Add schema changes as a **new numbered file** (zero-padded 3 digits) — never edit an applied one; the ledger now **enforces** this by checksum (a changed applied file aborts the run). Each file runs inside a transaction, so `CREATE INDEX CONCURRENTLY` / `ALTER TYPE … ADD VALUE` won't work in a migration.

(5) **`withTimeout` is structurally unsound while backgrounded — everywhere it's used. - **D1 follow-up debt (2026-09-02):** five items (4 from D1, item 5 found during D3 device smoke). **Item 3 fixed in D3 (2026-09-03); items 1, 2, 4, 5 remain.**
  1. **Set the `vision` phase deadline against measurement.** `PHASE_DEADLINE_MS.vision` is `null` — needs ≥5 backgrounded `vision`-phase durations from the new `frame.phase` logs (`appState ≠ 'active'`, `prevPhaseMs` on the `vision → api_post` transition), with the Arabic/Tesseract path exercised in at least two, before setting a deadline at ≈1.5× observed p95 (floored 30s, below `OCR_LOCK_LIVENESS_MS`, a whole multiple of `NATIVE_TICK_INTERVAL_MS`).
  2. **`TesseractOcr.recognize` abandons its promise on any throw, poisoning the single-flight for the rest of the session.** `TesseractocrModule.java` (node_modules `@devinikhiya/react-native-tesseractocr`) runs recognition in `new Thread(){ run(){ … promise.resolve() } }` with **no try/catch inside `run()`** — the outer try/catch covers only thread creation and `getBitmap`. Any throw from `createTesseractAPI` / `TessBaseAPI.init` (returns `false`, unchecked) / `setImage` / `getUTF8Text` / native leaves the promise permanently unsettled. Consequence: `activeRecognition` in `mobileArabicOcr.ts` clears in a `finally` that only runs if the promise settles — it never does, so **every subsequent Arabic OCR call for the rest of the session returns the same dead promise**; Arabic/Derja OCR is dead until app restart. Backgrounded-only (foregrounded, `withTimeout(…, '')` fires and the `finally` clears cleanly) — a consequence of the same unsoundness, not an independent bug. D1's phase deadlines cannot fix it: `forceReleaseProcessingLock` touches hook-scoped refs only, while `activeRecognition` is module state in `mobileArabicOcr.ts`. Since the keyword filter targets Tunisian Derja specifically, this is a detection gap, not a robustness nicety. Fix has a JS-only half (clear `activeRecognition` on the `withTimeout` fallback path — converts "dead until restart" into "one lost frame", doesn't need to wait on the native half) and a `patch-package` half (try/catch/finally in `run()` → `promise.reject`).
  3. **FIXED in D3 (2026-09-03) — `processCapturedFrame`'s `finally` no longer zeroes `processingStartTimeRef` outside the generation guard.** The `processingStartTimeRef.current = 0;` line moved from *above* `if (processingGenerationRef.current === generation) { … }` to *inside* it, next to the already-guarded `isProcessingRef.current = false` and D1's `setPhase('idle')` — the three `finally` resets are now uniformly generation-guarded. Recon (`D3` plan) established this was **one line corrupting four readers**, three harmed on every late stale `finally`: (a) `shouldForceReleaseProcessingLock` early-returns on `<= 0` → the A3c-2c 60s backstop is silently disabled for the *active* successor frame (worst on `vision`, whose phase deadline is `null` — no other backstop); (b) the takeover check at `processCapturedFrame`'s top computes `Date.now() - 0` → spurious immediate OCR-lock takeover of a healthy frame; (c) the heartbeat's `processingStartTimeRef.current === 0` self-clear terminates the active frame's own liveness interval early; (d) the heartbeat's `elapsed` is computed against `0`. Sites A (`forceReleaseProcessingLock` — no `generation` in scope, bumps the generation itself) and B (takeover branch — synchronously overwritten by the acquire write three lines later) are correct for **structural** reasons and were deliberately left alone; the watchdog reset was already guarded. Verified: 330 mobile tests (2 new pure `decideTickAction` invariant guards in `adaptiveCapture.test.ts` — real stamp → backstop fires, zeroed stamp → `noop`), `tsc` 9/9, lint delta zero. **Two-arm device smoke (2026-09-03, 2508CRN2BE, app-backgrounded + screen-on, temp `DEBUG_SIMULATE_FINALLY_RACE` scaffold since removed):** identical staged interleaving both arms — frame 1 parked in `vision`, `tick-liveness` force-released it at `elapsed≈64827` (gen 1→2), frame 2 acquired gen 3 and parked, frame 1 then resumed and ran its `finally` stale (`staleGeneration:1, activeGeneration:3`). **Arm 1** (`willZeroActiveStamp:true`, pre-D3 behaviour re-injected): frame 2's stamp zeroed → **no further `tick-liveness` ever fired** (6+ periodic ticks over 2 min, all `capture.skipped`, monitoring silently dead). **Arm 2** (D3 fix, `willZeroActiveStamp:false`): frame 2's stamp intact → `tick-liveness` force-released it at `elapsed:60050` ≈ 60 s after *it* parked, and the healthy ~60 s recovery cycle continued (frame 3, `tick-phase-timeout:foreground_lookup`, …). `processCapturedFrame` has no test harness, so the moved line itself is device-smoke-verified only.
  4. **Same `finally`, same bug class, one line below — `pendingFrameRef` read/null is unconditional.** `const deferredFrame = pendingFrameRef.current; pendingFrameRef.current = null;` (immediately after item 3's block) runs regardless of generation. A superseded frame's late `finally` therefore **steals the pending frame the *active* frame just enqueued** — via the takeover branch's `pendingFrameRef.current = event`, or a coordinator `BUSY_DEFERRED` coalesce — and the active frame's own `finally` then finds `null` and never re-issues that deferred capture: a silently dropped frame. Out of D3's scope (`processingStartTimeRef` only). Fix shape: guard the read+null inside `if (processingGenerationRef.current === generation)` like the rest of the block — but it needs its own verification pass, because the deferred re-issue logic just below (`isProcessingRef`, `coordinatorRef.current.takePendingReason()`, `triggerAppSwitchCapture(APP_SWITCH_DEFERRED)`) has interactions D3 did not touch.
  5. **The A3c-2c native-tick liveness backstop does NOT survive *screen-off* — only *app-backgrounded, screen-on*.** D3's device smoke measured this directly: with the screen slept (`KEYCODE_SLEEP`), JS froze completely for the full 185 s hold and `tick-liveness` fired at `elapsed: 195233` — i.e. **only on screen-on thaw**, not at 60 s. With the app backgrounded but the screen kept on (`stay_on_while_plugged_in`), it fired at `elapsed≈60000` every cycle, matching the three recorded incidents (all of which, re-examined, were screen-on). So `NATIVE_TICK_INTERVAL_MS`'s "Doze-resistant … keeps the process unfrozen for the whole session" is true for the *native* `Handler.postDelayed` loop but **not** for the JS `DeviceEventEmitter` listener it drives — MIUI freezes the RN JS thread on screen-off despite the `mediaProjection` FGS. Consequence: a frame that wedges while the phone is locked is unrecovered until the user wakes the screen (then recovered promptly). Not a D3 regression (D3's fix is correct in both states); it bounds what *any* JS-side backstop — A3c-2c or D1 — can promise. A real fix would need the force-release to run in native (e.g. the tick loop itself checking a last-progress timestamp the bridge updates), which is a native change deferred with the rest of the `withTimeout` root-cause work.

## Working across both apps

- API contract changes touch **both** sides: a backend route/shape change needs the matching `MobileApp/src/services/*Api.ts` update. There is no shared/generated type package — types are duplicated by hand.
- The mobile app assumes the backend is reachable at the configured LAN IP on port 3000. "JWT error / start backend" on the app's loading screen means the backend isn't up or the IP is wrong.
